# Architecture rules

- Prospect sign-in lives at /portal/sign-in while staff keep /auth; portal path refresh uses one private user topic with data-free stage/call signals, refetches through portal_my_path on join and tab visibility, and never polls or exposes staff candidate rows.
- Process advancement buttons reuse the pipeline move confirmation and compliance checks; both score-editing surfaces reuse QualificationSection; candidate selection stays in the URL by database ID, and portal call dates use source_process_step + 1 because each process step schedules the next conversation.

- Homework deadline offsets come from portalPath and use calendar days in the viewer's browser time zone; staff homework summaries read candidate-scoped portal submissions and ticks alongside staff checks, so signed-form completion is not inferred from a staff checkbox.

- Keep mailing address validation in the pure shared function module, reused by the browser and lead-push function, so both enforce the same rule.
- Auth access is cleared on every session event and lookup results are accepted only for the latest session request, so account switching cannot reuse another account's staff role.
- Unsubscribe sync accepts only a verified staff session or the timer's vault-stored pass (checked and rate-limited to once per 20 hours by a service-role-only database function), so the timer never depends on the managed server key; manual controls stay available when mailbox loading fails, and the UI's timestamps describe new suppressions rather than job runs.- Staff access comes only from public.user_roles rows granted on purpose (never by the signup trigger); prospect portal accounts link to one candidate via candidate_portal_users and are routed to /portal, so prospects can never read staff data.
- Prospect portal forms are typed configs in src/lib/portalForms rendered by one generic page; signing goes only through the portal-submit-form function, which locks the form and writes an append-only signature/audit row, so signed answers can never be edited by the prospect.
- RFC submissions resolve their saved form version for read-only views/history; ZIP lookup uses a lazy-loaded local US list, and submitted References show beside separate staff call notes so neither overwrites the other.
- Conditional school fields use the form config's showWhen predicate for entry, review, and PDF rows, so hidden answers cannot appear in a new submission's PDF.
- Staff Prospect Forms is candidate-scoped; correction requests use a staff-verified locked action to copy immutable submission snapshots into working drafts, while all previous signatures/PDFs remain available. Submission completion is atomic and service-role-only so repeated calls cannot produce competing records.
- Prospect email notices use registered templates on the existing app-email rail; saved stage/call changes trigger asynchronous server-only sends, keyed by opened step or call/time, and recipients must match a non-staff portal account. Database triggers cover manual and process calls without browser-dependent sends; reminders require a separate approved phase.
- Auth invitation copy uses the signed webhook's portal setup destination to select prospect-only wording; all recovery and staff invitation paths retain their own copy, and confirmation links are passed through unchanged.
- Google revision conflicts accept a read-back only for identical ready scheduled calls and identical provider results; genuine conflicts return a normal result and never authorize local deletion or overwrite newer details.
- All call tools sync through candidateEvents and a staff-only Google action; stable IDs prevent duplicate retry invites, cancellation precedes local deletion, completed history stays intact, and edits preserve notify_prospect. Database pending/revision guards release app notices only after Google confirms the current call and Meet link; portal_my_path exposes only that prospect's ready Meet URL.

## Item 23 receipt + FDD version rules
- Staff FDD sends use the existing app-email rail and snapshot one version in fdd_email_sends; only a provider-accepted sent log atomically records delivery/date. The shared database gate protects FDD downloads and new Item 23 signatures; prior staff send records count, and resends never rewrite signed receipt evidence.
- The FDD version a prospect received resolves in one order: `candidate_compliance.fdd_file_id` (staff-recorded) first, else the prospect's earliest `fdd_delivery_events` row; prospects read it through the security-definer RPC `portal_my_fdd_version()`. The Item 23 receipt must name that version's issuance date — never the newest FDD. If no version can be confirmed, signing is blocked with a contact message.
- The Item 23 signing date writes `candidate_compliance.fdd_received_at` (only when empty) and appends a `receipt_signed` row to `fdd_delivery_events`; both live in `portal-submit-form`.
- Item 23 corrections pin the source signature's FDD ID, preserve the first received date, and append receipt_corrected events linked to the correction request; proof packets include all receipts and identify each receipt/event's saved FDD version separately from today's staff selection, so later changes cannot hide original evidence.
